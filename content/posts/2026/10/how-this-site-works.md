之前用的是 Hexo 加一个二次元主题。文章存在本地，改一篇要 `hexo g && hexo d`，图片得先扔进 `source/images` 目录再重新构建。想随手发两段话，流程比写那两段话本身还长。

现在换成一个 Go 写的小服务，跑在一台 403 MiB 内存的阿里云 ECS 上。

## 为什么是 Go

不是因为时髦。403 MiB 里要装系统、反向代理和一个动态服务，能选的东西不多：

- Go 编译成单个静态二进制，跑起来常驻 30 MB 左右
- 模板和 CSS 用 `embed` 打进二进制，部署时只传一个文件，不会出现"代码更新了但模板忘了传"
- 交叉编译在 GitHub Actions 里做，服务器不需要装 Go——也装不了，`go build` 峰值要吃 1 GB 内存，403 MiB 的机器会被内核直接 OOM 掉

Python 的 FastAPI 空载就是 70–100 MB，Node 更重。PHP-FPM 配 Nginx 是两个进程加起来 100 MB 出头，也能用，但部署和调优都更麻烦。

## 数据放在哪

文章是磁盘上的 markdown 文件，不是数据库里的 blob。这样出问题能直接 `cat` 出来看，也能被 git 管版本。

评论是一个 JSON 文件。个人博客的评论量在几千条这个量级，全量内存加全量落盘完全够用，换来的是可以直接读、可以进 git 做 diff、不用养一个数据库进程。所有写操作在进程内加锁串行化，不会并发写坏文件。

## 图片为什么不做处理

一开始想过在服务器上缩放图片，后来放弃了。Go 的 `image` 包必须把图完整解压进内存才能操作，一张 4000×3000 的手机照片就是 48 MB，而这台机器总共只有 403 MiB。

所以现在图片是原样存的：文件从网络直接落到磁盘，内存里只有一块 32 KB 的缓冲，服务端连解码都不做，只检查前 512 字节是不是真的图片。代价是读者要下载原图，用 `loading="lazy"` 缓解——滚到跟前才加载。

## 关于这个页面

全站一个 CSS 文件，十行。没有框架、没有图标字体、没有圆角阴影渐变。文字收在中间一栏，不贴着屏幕边，也不像手机阅读器那种窄栏。

字体交给浏览器默认的衬线。中文落到宋体，字号够大就不糊。

这就是 [How To Ask Questions The Smart Way](http://www.catb.org/~esr/faqs/smart-questions.html) 那个页面的做法：它一个 CSS 都没有，`<body>` 上连 style 属性都不写。干净不是因为设计得好，是因为什么都没加。
